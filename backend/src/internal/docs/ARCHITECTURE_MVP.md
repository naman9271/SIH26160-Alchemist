# IPsec Analyzer MVP Architecture — Normative Contract

This document is the source of truth for the current MVP. The larger Sensor,
Core and Fusion catalogues describe a roadmap. If a roadmap section conflicts
with this document or a checked-in protobuf, this document and the protobuf
take precedence.

## Process boundaries

```text
Browser -> Next.js server route/BFF -> Go Core
                                   -> internal Sensor
                                   -> internal Fusion
                                   -> security/risk/report modules
                                   -> Python TrafficClassifier over gRPC
```

- Sensor and Fusion are Go packages in the Core process. They are not public
  network services.
- Only Core services are registered by `src/cmd/server`.
- The browser must not call native gRPC directly. The Next.js server layer
  will translate browser HTTP requests to the Core contract. `/live` and
  `/health` are the only implemented HTTP endpoints today.
- The canonical Python contract is
  `backend/ml-service/proto/ml/v1/traffic_classifier.proto`. Go stubs are generated by
  `backend/Makefile`.

## Ownership

- Sensor observes packets, parses IKE/ESP/AH/NAT-T, creates metadata-only flow
  windows and reads VICI/XFRM when configured.
- Python classifies encrypted application traffic and owns class probability,
  calibrated confidence, `is_unknown`, model version and optional SHAP.
- Fusion correlates evidence and records provenance. It preserves Python's
  UNKNOWN decision and never applies a second classifier threshold.
- Security/risk evaluates fused facts after primary fusion. A security finding
  may reference a conclusion but may not create or override protocol facts.
- Protocol facts such as IKE version, cipher, SPI, DH group, PFS and SA mode
  are deterministic Sensor/gateway responsibilities, never ML inputs.

## Canonical evidence status

| Value | Number | Meaning |
|---|---:|---|
| `OBSERVED` | 1 | Directly present in captured traffic |
| `DERIVED` | 2 | Deterministically computed from observations |
| `INFERRED` | 3 | Probabilistic output, including ML |
| `VERIFIED_GATEWAY` | 4 | Read from trusted VICI/XFRM gateway state |
| `UNKNOWN` | 5 | No supported conclusion |

## Canonical traffic feature policy

- Fixed 10-second per-flow windows.
- First observed direction is upload; opposite direction is download.
- Direct ESP and UDP-encapsulated ESP are accepted; IKE and NAT keepalives are
  excluded from classifier windows.
- Directional ESP SPIs remain protocol evidence but are not part of the
  bidirectional ML-flow key.
- Timing values sent to Python use seconds.
- Feature names and ordering exactly match Python `FlowFeatures`; no missing
  field is silently invented.
- The safe live-stream policy is `DROP_FEATURE_WINDOW`; blocking packet capture
  is rejected.

## MVP delivery order

1. Input/live acquisition and one shared packet pipeline.
2. Deterministic protocol evidence.
3. Exact ML feature extraction and optional Python inference.
4. Primary evidence fusion.
5. Security findings, risk score and threat matrix.
6. Reports and dashboard integration.

The reproducible VPN testbed is a separate lab asset. It may create VPNs and
traffic, but the analyzer remains read-only.
